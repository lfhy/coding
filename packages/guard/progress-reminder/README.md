# @deepseek-ai/dsh-progress-reminder

长任务的进度提醒上下文。一个轮次内连续完成的工具调用达到阈值而模型始终没有向用户说话时，循环在下一次模型请求前注入一条系统提醒，要求先汇报进度再继续执行。Coding 组合默认启用它，节奏由 `toolCallsPerReminder` 控制。

## 配置

```yaml
- id: progress-reminder
  name: '@deepseek-ai/dsh-progress-reminder'
  config:
    toolCallsPerReminder: 15 # optional; omit for the shipped default
```

`toolCallsPerReminder` 是每次提醒之间允许连续完成的工具调用数，默认 `15`，必须是正的安全整数；其他值在插件加载时失败。计数单位是一次已完成的工具调用（一条 `tool/result` 事件），不是模型调用的轮次，所以一次并行批次可以跨过阈值，提醒文本会写出真实的累计数。

## 计数与注入时序

插件追加一个 `agent/pre-step` 监听器，先行委托下游，再把提醒追加到将要进入步骤的消息批次末尾。因此提醒与它所属的请求同批写入日志，被下游拒绝、监听器失败或轮次信号已中止时不会留下任何记录。

计数完全从会话日志派生：从尾部回扫，遇到本插件上一次注入的提醒、或上一个轮次的 `turn/end` 就停止，统计区间内已完成的 `tool/result` 数。插件不持有进程内状态，所以恢复、fork 与压缩遮蔽后的计数一致，不会因为漏记一次分发而少提醒或多提醒。轮次边界同时是计数边界：模型已经用最终答复向用户说过话之后，下一个轮次从头累计。

提醒是持久的用户消息（来源 `{ kind: 'plugin', plugin: 'progress-reminder' }`），会留在派生历史中直到压缩遮蔽。`./invariant` 配套模块校验每条提醒的文本逐字等于渲染结果，且声明的调用数等于该边界之后的真实计数。

## 模型体验

### 连续工具调用后的进度提醒

#### 模型看到的内容

提醒是一条 `<system-reminder>` 区块，插在触发它的那次工具结果之后、下一次请求之前。`<tool-calls>` 是该边界之后真实完成的工具调用数。

提醒点名"回复正文"并说明用户看不到思考过程：推理块在客户端默认折叠，模型把进度写在推理里时用户读不到，所以正文是唯一有效的汇报位置。模型可以在同一条助手消息里同时输出正文与工具调用，因此汇报不需要额外停下工具循环。提醒还要求先把待办列表更新到与事实一致：长任务里列表过期和用户看不到进展是同一个问题的两面。

##### 提醒文本

```markdown
<system-reminder>
你已连续执行 <tool-calls> 次工具调用，其间没有向用户汇报过进展。
用户看不到你的思考过程，只能看到回复正文。
现在先用计划工具把待办列表更新到与事实一致，再在正文里写一段简短的进度说明：已完成什么、还剩什么、有没有需要用户拍板的地方。然后继续执行剩余任务。
</system-reminder>
```

#### Token 影响

每条提醒只注入一次，并保留在请求历史中直到压缩将其遮蔽；典型轮次只有一到两条。

#### KV Cache 影响

仅追加；新可见内容位于可复用请求前缀之后，不会使现有 KV Cache 条目失效。

## 已知限制与暂缓事项

- **只提醒，不强制**：提醒是模型可见的指令，模型可以不汇报而直接继续调用工具；本包不做回复拦截或轮次中断。
- **正文位置靠模型遵守**：提醒明确要求把说明写进回复正文，但模型仍可能把它写进推理块，此时用户在折叠内容之外看不到任何进展；客户端不解析正文，因此不对汇报内容做校验或补写。
- **待办那句假定部署有计划工具**：组合里没有待办工具时，模型会忽略"更新待办列表"这一句；插件不检测工具是否注册。
- **按会话阈值固定**：阈值是插件配置，不是逐会话或逐轮次的覆盖；同一 Host 上的所有 agent 共用它。
- **不区分工具**：任何已完成的工具调用都计数，包括快速只读查询；需要精细节奏时用触发工具的部署组合自行调整阈值。

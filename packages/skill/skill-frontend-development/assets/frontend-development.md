# Frontend development

Use this skill when creating or modifying a frontend, web page, component, or user interface. The product UI is the user-facing result: implementation instructions, system prompts, internal tool names, and defensive process language must stay out of the page unless the product explicitly makes them user content.

## Reading bundled files

Read a bundled file with the `skill_read` tool: `skill_read { "name": "frontend-development", "path": "examples/index.md" }`.
Paths are relative to this skill's resource root, never absolute and never containing `..`.

When the current host has no `skill_read` tool, fall back to the resource prefix shown in `<skill_resources>`: pass
that prefix verbatim plus the same relative path, for example
`${INTERNAL_SKILL_DIR}/coding-skill-frontend-development/examples/index.md`. The prefix already points at this
skill's `assets/` directory, so never append `assets/` a second time, and never resolve it with a shell command: it
is a workspace alias understood by the file tools, not an environment variable, so `ls` or `cat` on it reports
"not found".

## Before editing

1. Read the repository and the target package instructions, then locate the existing page, route, component, UI primitives, design tokens, styles, tests, and reference screens that own the requested behavior.
2. Reuse the project's current framework, language, build system, component library, UI modules, design tokens, icons, layout primitives, and interaction patterns. When the project has no shared component for child tabs, modal dialogs, Toasts, auth pages, settings pages, or list pages, read [`examples/index.md`](examples/index.md) and copy the matching example into that shared layer instead of writing a page-local variant. If the project has an established icon system, use its public entry point and semantic mappings. If it does not, read [`icon-library.md`](icon-library.md) and use Lucide as the default recommendation. Do not replace the project's visual system or create a parallel component set for one page.
3. Treat the project's icon system as part of its component system. Inspect the public icon exports and semantic mappings before adding visual controls. Prefer icons for navigation, actions, object types, statuses, and repeated row or card anchors. Import through the supported public entry point; do not hand-draw or inline SVG, use emoji or arbitrary Unicode as interface icons, or add a second icon library for one screen. If no suitable library icon exists, use a familiar generic icon with a short label; only introduce a custom asset as a last resort behind the project's icon abstraction or asset pipeline. When the surface genuinely needs an illustration or a domain symbol the project lacks, do not invent it as a hand-written SVG: draw a base plate first with the image tool (`generate_image`) at the final display size, viewpoint, stroke weight, and palette, inspect the returned image, then rebuild it as a clean SVG behind the project's icon abstraction or asset pipeline, or ship the raster asset. Without image tools, fall back to a library icon with a label and state that the illustration is missing instead of hand-tracing paths.
4. Route transient user notifications through the project's shared Toast or notification service. Do not add one-off inline success/error banners, fixed alert boxes, browser `alert()`, or page-specific notification markup for events that should briefly acknowledge an action. Keep persistent validation, blocking errors, and task-relevant guidance in the owning surface; use Toast for short-lived global feedback and make it accessible with the shared live-region and focus behavior.
5. Keep implementation context separate from product content before writing any visible string. Never render system or developer instructions, prompts, skills, tool calls, agent plans, framework or library names, package or component identifiers, file paths, internal URLs, raw JSON or schemas, code, stack traces, debug logs, or internal status labels as UI copy. This applies to headings, descriptions, placeholders, toasts, empty/error/loading states, tooltips, accessible names, alternative text, and links. Translate failures into concise product language that says what happened and what the user can do; never interpolate raw exceptions, JSON, or internal response data. Only content the user supplied and explicitly asked to inspect may appear verbatim in a dedicated code or content surface, and it must not be mixed with product controls or internal status text.
6. Keep page composition and feedback reusable. Read [`notification-and-structure.md`](notification-and-structure.md) before introducing a new page, notification, empty state, or shared-looking component. Extend an existing primitive or feature boundary instead of creating page-local copies of buttons, dialogs, Toasts, spacing scales, icon wrappers, loading states, or error surfaces.
7. Design motion as part of the interaction contract, not decoration. Do not hard-cut between sibling pages or major same-page states when the existing stack can preserve context and animate the change. Prefer the project's CSS Modules, motion tokens, `transition`, and `@keyframes`; use JavaScript animation only when CSS cannot express the required gesture or physics. Keep the transition short, directional, and tied to the state change so focus, content hierarchy, and the next action remain clear. For a starting point, read [`motion-recipes/index.md`](motion-recipes/index.md) and copy only the matching CSS recipe.
8. Use restrained micro-interactions for icons and controls when they clarify cause and effect: rotate or translate a chevron on disclosure, give a status icon a subtle state animation, and animate add/remove or success/error feedback without shifting unrelated layout. Do not animate every icon, use perpetual motion for decoration, or make an icon animation the only state signal. Preserve stable layout and avoid animating large areas, `width`/`height`, or other layout-triggering properties when `transform` or `opacity` is sufficient.
9. Do not start a frontend implementation from blank files when an existing page, component, slot, template, or project scaffold can be extended. For a new project, do not hand-write a foundation from zero: initialize with a maintained modern scaffold and use an established reference template such as shadcn, shadcn-admin, or Headless UI plus Tailwind CSS when it matches the project's chosen stack; adapt it to the project instead of hand-writing a competing foundation.
10. Never ship a browser-default control. An unstyled or lightly styled `<input>`, `<select>`, `<textarea>`, `<button>`, `<input type="search">`, `<input type="date">`, checkbox, radio, or color input is a defect, not a shortcut: `input type="search"` brings the platform magnifier, clear button, and rounded white box; `select` brings the native arrow and native popup; checkboxes and radios bring the platform glyph. Use the project's accessible Button, Input, SearchField, Select, Textarea, Dialog, Menu, and Tabs primitives, or their established equivalents, so height, radius, border, surface, placeholder, focus ring, and disabled state come from the theme. Preserve keyboard operation, focus visibility, labels, error association, loading state, disabled state, and reduced-motion behavior.
11. A missing primitive is a task, not an excuse: when the project has no field, search, select, or textarea primitive yet, add one shared component (see [`examples/fields/`](examples/fields/TextField.tsx)) and use it everywhere. Only the project's own token-based component may reach the DOM as a control; a raw tag is acceptable solely inside that shared primitive.
12. Design every primary flow to remain usable within one viewport (`100vh` or the product's viewport-safe equivalent). A page that grows taller with its data is a defect: the document itself must not scroll when rows arrive. Avoid pages that become an unbounded vertical document; keep the main action and current context visible, put long content in the owning region's scroll area, and use responsive overflow rather than shrinking controls until they are unusable. On a list, table, log, inbox, or search-results page the document itself must not scroll: the page owns `100vh`, the header and the search and filter toolbar stay outside the scroll container, and only the list body scrolls, so moving through rows never moves the toolbar. Every motion recipe must preserve its `prefers-reduced-motion` fallback.
13. Treat long collections as virtualized and incrementally loaded regions. Render only the visible window plus a small overscan once the collection can exceed a viewport of rows, and load the next page from an end-of-list sentinel or the virtualizer's visible range near the end instead of fetching everything up front. Reuse the project's existing virtualization, query, and pagination primitives; if none exist, add one product-wide virtualizer rather than a per-page scroll workaround. Read [`list-scroll.md`](list-scroll.md) before building or fixing a list page. A page-scrolling list, an unbounded mounted row count, and a full collection fetched before the first screen are defects, not acceptable tradeoffs.
14. Keep the list inside the viewport width with uniform, single-line rows. Long names, titles, paths, and emails end with an ellipsis inside their column instead of wrapping, every row in a list has the same height, and the page never scrolls horizontally. When the columns do not fit, hide lower-priority ones by breakpoint or a column chooser and keep the identity column and row actions visible; never solve a width problem by wrapping a cell, letting the table widen the page, or squeezing a column below legibility.

15. Align every row on one vertical center. Use one grid template and a fixed row height with `align-items: center`; every cell is a flex row whose children are centered, leading dots and avatars sit in fixed-size boxes, chips are inline flex with their own line height, and numbers use tabular figures. Header cells reuse the same template and alignment. A cell that drifts high or low — typically a badge inheriting the row's line height, or a flex row left at `flex-start` — is a defect; read [`list-scroll.md`](list-scroll.md) "Row alignment".

## Copyable examples

[`examples/index.md`](examples/index.md) indexes reviewed shapes for the surfaces that drift most: child
tabs, a modal dialog, a shared Toast, an auth page, a settings page whose "change password" form lives in a
dialog, and a list page whose header and toolbar stay put while the body scrolls. Copy the matching example into
the project's shared UI layer, map its `--ui-*` seams onto the product's semantic tokens (light and dark), and
keep its ARIA and keyboard wiring exactly as written. One shared copy per concept: a page imports it, it never
restates it.

## Page shell and scrolling

Every page owns the viewport: `height: 100dvh` (or the product's viewport-safe equivalent) on the shell,
`min-height: 0` on every flex or grid child between the shell and a scroll region, and `overflow: hidden` on the
shell itself. Only a list, table, log, transcript, or detail body scrolls; the document does not. A page whose
height grows with its data — a dashboard that keeps stretching as activity rows arrive, a card list that pushes
the footer off screen — is a defect, not a tradeoff.

Bound each card or panel list: `min-height: 0` plus `overflow: auto` inside the card, a fixed or clamped height
that matches its sibling panel, single-line rows, and a "View all" action that opens the full set in a dialog, a
drawer, or an expanded panel with its own scroll area. Keep the page height equal to the viewport at any row
count. Starting point: [`pages/dashboard-page.tsx`](pages/dashboard-page.tsx).

## While implementing

- Keep the user goal and next action obvious. Prefer a clear hierarchy, useful defaults, concise labels, recoverable errors, and visible success/loading/empty states over implementation detail.
- Compose a product surface, not a text poster. Use the existing icon library as visual anchors for navigation, actions, object types, and statuses; pair icons with concise labels when clarity needs text. Icons do not replace an accessible name, and unclear icons need a short visible label or tooltip. Avoid oversized hero headings, long decorative paragraphs, slogan-like copy, ASCII or emoji art, and large text blocks used as decoration when a control, icon, status, or data component would communicate the intent.
- Match nearby screens for spacing, typography, color, radius, surface, icon size, responsive behavior, and interaction feedback. Use semantic theme tokens and existing CSS or styling conventions; do not introduce literal colors, one-off breakpoints, arbitrary shadows, or a second component library without a project-level reason.
- Own the scroll in exactly one place: the list viewport. The page shell, header, search field, filter toolbar, and list actions stay outside it and keep their position while rows scroll. Do not put `overflow: auto` on the page, do not nest a second scroll container inside a row, and do not fake a fixed toolbar with `position: sticky` over a page-level scroll. Give the viewport a real height through the layout chain (`min-height: 0` on flex ancestors, `100dvh` where mobile browser chrome shrinks the viewport), and reset it to the top when the filter or query changes.
- Keep the list body virtualized and progressively loaded. Render only visible rows plus overscan, keep scroll position, selection, and focus when a page is appended or the user returns to the list, and reserve dynamic row measurement for content streams whose rows legitimately span more than one line, such as a log or transcript, never for a list row that failed to truncate. Deduplicate page requests, cancel stale ones on filter changes, and put loading, retry, and end-of-list states in the list tail rather than replacing loaded rows. When infinite scroll is the only trigger, provide a keyboard path to load more and announce appended results through the shared live region.
- Keep rows one line and one height. Give each column an explicit width budget and let the cell clip its text: `min-width: 0` on flex ancestors, `minmax(0, 1fr)` in grids, and `white-space: nowrap; overflow: hidden; text-overflow: ellipsis` on the truncating cell. Do not let a badge, avatar, button, tag list, or second line of text change a row's height, hide low-priority columns when the width runs out instead of wrapping or widening the page, and expose each truncated value in full through the shared tooltip or the row detail so the ellipsis hides characters rather than information.
- Use hierarchy intentionally: use child tabs for sibling views within a page, drawers for contextual detail or secondary editing, and modal dialogs for focused decisions or short forms. Keep each layer local, dismissible, keyboard-accessible, and sized to preserve the underlying context. Do not put a long multi-section workflow into one tall modal: split it into a step-based modal or wizard with one focused task per step, a visible step indicator, Back/Next controls, validation at the step boundary, and a final confirmation. Use child tabs inside a drawer when the drawer contains several related detail views; keep the drawer for contextual work and do not turn each tab into a separate page.
- Keep model, agent, system-prompt, tool, framework, or implementation wording out of user-facing copy. Translate internal states into product language that explains what the user can do or what happened. Do not expose implementation-facing instructions, prompt fragments, debugging vocabulary, or process narration in the UI. Before finishing, inspect every user-visible string, including fallback branches, errors, empty states, loading states, tooltips, aria labels, and data-derived labels; if a phrase describes how the app is built rather than what the user can do, remove it or replace it with product language.
- Do not turn secondary operations into another full page or an always-visible nested form. A create action must open a modal dialog (or an existing drawer when the flow genuinely needs more room); the page shows the create trigger, not the create form as a same-level content block. Use the least intrusive layer that fits the task: child tab for peer content, drawer for contextual work, modal for focused create/confirm flows.
- Do not fill the interface with defensive warnings, policy disclaimers, or speculative failure text. Show a warning only when it changes the user's decision, and explain the concrete action or consequence in the smallest useful wording.
- If the product needs transparency, show user-facing plan items, progress, current status, decisions, results, and actionable errors—not implementation prompts or internal process narration.
- When the user explicitly names or clearly asks for a named visual direction ("make it look like Stripe", "cyberpunk dashboard", "glassmorphism", "brutal style"), load the `stylekit` skill and follow its style spec: pick the exact slug, take its colors, tokens, and do/don't rules, then implement them with this project's existing components and theme layer. The spec guides the visual decisions; it does not replace product behavior, accessibility, or the project's own stack.
- When a requested behavior conflicts with the existing stack or UI modules, inspect their contracts and extend the owning abstraction rather than bypassing it in a local component.

## Verification

1. Run the narrowest relevant tests and type/lint/build checks for the changed package.
2. Build or start the real application path when the change affects a rendered page; do not validate only an isolated component or source file.
3. Check that the primary flow fits within the target viewport and that long content scrolls inside the correct region instead of creating an accidental full-page scroll. Fill the page with a few hundred rows and confirm `document.documentElement.scrollHeight` stays equal to the viewport height: the shell is `100dvh`, the list or panel body scrolls, and no card in a dashboard pushes the page longer. On a list page, confirm the document itself is not scrollable, the header and search or filter toolbar keep their position while the list scrolls, and the list viewport is the only scroll container.
4. Verify list scrolling in the running app: the DOM keeps a bounded number of rows while the user scrolls, the next page loads before the end with visible loading and end-of-list states, a filter change returns the list to the top, and appending a page preserves scroll position and keyboard focus.
5. Check row alignment at 2× zoom: a horizontal line through the middle of a row crosses the middle of every cell in it (dot, label, chip, timestamp, row action), and the header uses the same template. A cell sitting high or low is a defect.
5. Check the list's width and row rhythm at representative narrow and wide widths: the page has no horizontal scroll, low-priority columns are hidden instead of squeezed, every row reports the same height, long names are ellipsized on one line rather than wrapped, and the full value stays reachable by hover, focus, or the row detail.
6. Check that tabs, drawers, and modal dialogs create the intended hierarchy: a create trigger opens its form in a dialog or contextual drawer, rather than rendering the form beside the trigger at the same level.
7. When the change followed a `stylekit` style spec, compare the rendered result against that spec's tokens and rules, including computed colors, typography, spacing, borders, and the required interaction states.
7b. Inspect every control on the page in the running app: a platform-default search box, select arrow, checkbox glyph, date picker, or focus ring means the primitive was skipped. The field height, radius, border, surface, placeholder color, and focus ring must match the rest of the product, and a search field must keep its own clear action.
8. After implementation, load `browser-use` and use its structured browser tools to inspect the real rendered page. Check the target flow, keyboard/focus behavior, loading/empty/error/success states that are relevant, and responsive layouts at representative widths. Read each returned observation before the next browser action and use only the latest visible element references.
9. Keep the browser page open for the user unless they ask to close it. Report checks that could not run and why.

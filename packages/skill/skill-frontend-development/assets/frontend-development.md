# Frontend development

Use this skill when creating or modifying a frontend, web page, component, or user interface. The product UI is the user-facing result: implementation instructions, system prompts, internal tool names, and defensive process language must stay out of the page unless the product explicitly makes them user content.

## Before editing

1. Read the repository and the target package instructions, then locate the existing page, route, component, UI primitives, design tokens, styles, tests, and reference screens that own the requested behavior.
2. Reuse the project's current framework, language, build system, component library, UI modules, design tokens, icons, layout primitives, and interaction patterns. If the project has an established icon system, use its public entry point and semantic mappings. If it does not, read [`assets/icon-library.md`](icon-library.md) and use Lucide as the default recommendation. Do not replace the project's visual system or create a parallel component set for one page.
3. Treat the project's icon system as part of its component system. Inspect the public icon exports and semantic mappings before adding visual controls. Prefer icons for navigation, actions, object types, statuses, and repeated row or card anchors. Import through the supported public entry point; do not hand-draw or inline SVG, use emoji or arbitrary Unicode as interface icons, or add a second icon library for one screen. If no suitable library icon exists, use a familiar generic icon with a short label; only introduce a custom asset as a last resort behind the project's icon abstraction or asset pipeline.
4. Route transient user notifications through the project's shared Toast or notification service. Do not add one-off inline success/error banners, fixed alert boxes, browser `alert()`, or page-specific notification markup for events that should briefly acknowledge an action. Keep persistent validation, blocking errors, and task-relevant guidance in the owning surface; use Toast for short-lived global feedback and make it accessible with the shared live-region and focus behavior.
5. Keep implementation context separate from product content before writing any visible string. Never render system or developer instructions, prompts, skills, tool calls, agent plans, framework or library names, package or component identifiers, file paths, internal URLs, raw JSON or schemas, code, stack traces, debug logs, or internal status labels as UI copy. This applies to headings, descriptions, placeholders, toasts, empty/error/loading states, tooltips, accessible names, alternative text, and links. Translate failures into concise product language that says what happened and what the user can do; never interpolate raw exceptions, JSON, or internal response data. Only content the user supplied and explicitly asked to inspect may appear verbatim in a dedicated code or content surface, and it must not be mixed with product controls or internal status text.
6. Keep page composition and feedback reusable. Read [`assets/notification-and-structure.md`](notification-and-structure.md) before introducing a new page, notification, empty state, or shared-looking component. Extend an existing primitive or feature boundary instead of creating page-local copies of buttons, dialogs, Toasts, spacing scales, icon wrappers, loading states, or error surfaces.
7. Design motion as part of the interaction contract, not decoration. Do not hard-cut between sibling pages or major same-page states when the existing stack can preserve context and animate the change. Prefer the project's CSS Modules, motion tokens, `transition`, and `@keyframes`; use JavaScript animation only when CSS cannot express the required gesture or physics. Keep the transition short, directional, and tied to the state change so focus, content hierarchy, and the next action remain clear. For a starting point, read [`assets/motion-recipes/index.md`](motion-recipes/index.md) and copy only the matching CSS recipe.
8. Use restrained micro-interactions for icons and controls when they clarify cause and effect: rotate or translate a chevron on disclosure, give a status icon a subtle state animation, and animate add/remove or success/error feedback without shifting unrelated layout. Do not animate every icon, use perpetual motion for decoration, or make an icon animation the only state signal. Preserve stable layout and avoid animating large areas, `width`/`height`, or other layout-triggering properties when `transform` or `opacity` is sufficient.
9. Do not start a frontend implementation from blank files when an existing page, component, slot, template, or project scaffold can be extended. For a new project, do not hand-write a foundation from zero: initialize with a maintained modern scaffold and use an established reference template such as shadcn, shadcn-admin, or Headless UI plus Tailwind CSS when it matches the project's chosen stack; adapt it to the project instead of hand-writing a competing foundation.
10. Never use browser-default controls as the finished product UI. Use the project's existing accessible Button, Input, Select, Dialog, Menu, Tabs, and form primitives or their established equivalents. Preserve keyboard operation, focus visibility, labels, error association, loading state, disabled state, and reduced-motion behavior.
11. Design every primary flow to remain usable within one viewport (`100vh` or the product's viewport-safe equivalent). Avoid pages that become an unbounded vertical document; keep the main action and current context visible, put long content in the owning region's scroll area, and use responsive overflow rather than shrinking controls until they are unusable. Every motion recipe must preserve its `prefers-reduced-motion` fallback.

## While implementing

- Keep the user goal and next action obvious. Prefer a clear hierarchy, useful defaults, concise labels, recoverable errors, and visible success/loading/empty states over implementation detail.
- Compose a product surface, not a text poster. Use the existing icon library as visual anchors for navigation, actions, object types, and statuses; pair icons with concise labels when clarity needs text. Icons do not replace an accessible name, and unclear icons need a short visible label or tooltip. Avoid oversized hero headings, long decorative paragraphs, slogan-like copy, ASCII or emoji art, and large text blocks used as decoration when a control, icon, status, or data component would communicate the intent.
- Match nearby screens for spacing, typography, color, radius, surface, icon size, responsive behavior, and interaction feedback. Use semantic theme tokens and existing CSS or styling conventions; do not introduce literal colors, one-off breakpoints, arbitrary shadows, or a second component library without a project-level reason.
- Use hierarchy intentionally: use child tabs for sibling views within a page, drawers for contextual detail or secondary editing, and modal dialogs for focused decisions or short forms. Keep each layer local, dismissible, keyboard-accessible, and sized to preserve the underlying context. Do not put a long multi-section workflow into one tall modal: split it into a step-based modal or wizard with one focused task per step, a visible step indicator, Back/Next controls, validation at the step boundary, and a final confirmation. Use child tabs inside a drawer when the drawer contains several related detail views; keep the drawer for contextual work and do not turn each tab into a separate page.
- Keep model, agent, system-prompt, tool, framework, or implementation wording out of user-facing copy. Translate internal states into product language that explains what the user can do or what happened. Do not expose implementation-facing instructions, prompt fragments, debugging vocabulary, or process narration in the UI. Before finishing, inspect every user-visible string, including fallback branches, errors, empty states, loading states, tooltips, aria labels, and data-derived labels; if a phrase describes how the app is built rather than what the user can do, remove it or replace it with product language.
- Do not turn secondary operations into another full page or an always-visible nested form. A create action must open a modal dialog (or an existing drawer when the flow genuinely needs more room); the page shows the create trigger, not the create form as a same-level content block. Use the least intrusive layer that fits the task: child tab for peer content, drawer for contextual work, modal for focused create/confirm flows.
- Do not fill the interface with defensive warnings, policy disclaimers, or speculative failure text. Show a warning only when it changes the user's decision, and explain the concrete action or consequence in the smallest useful wording.
- If the product needs transparency, show user-facing plan items, progress, current status, decisions, results, and actionable errors—not implementation prompts or internal process narration.
- When the user explicitly names or clearly asks for a named visual direction ("make it look like Stripe", "cyberpunk dashboard", "glassmorphism", "brutal style"), load the `stylekit` skill and follow its style spec: pick the exact slug, take its colors, tokens, and do/don't rules, then implement them with this project's existing components and theme layer. The spec guides the visual decisions; it does not replace product behavior, accessibility, or the project's own stack.
- When a requested behavior conflicts with the existing stack or UI modules, inspect their contracts and extend the owning abstraction rather than bypassing it in a local component.

## Verification

1. Run the narrowest relevant tests and type/lint/build checks for the changed package.
2. Build or start the real application path when the change affects a rendered page; do not validate only an isolated component or source file.
3. Check that the primary flow fits within the target viewport and that long content scrolls inside the correct region instead of creating an accidental full-page scroll.
4. Check that tabs, drawers, and modal dialogs create the intended hierarchy: a create trigger opens its form in a dialog or contextual drawer, rather than rendering the form beside the trigger at the same level.
5. When the change followed a `stylekit` style spec, compare the rendered result against that spec's tokens and rules, including computed colors, typography, spacing, borders, and the required interaction states.
6. After implementation, load `browser-use` and use its structured browser tools to inspect the real rendered page. Check the target flow, keyboard/focus behavior, loading/empty/error/success states that are relevant, and responsive layouts at representative widths. Read each returned observation before the next browser action and use only the latest visible element references.
7. Keep the browser page open for the user unless they ask to close it. Report checks that could not run and why.

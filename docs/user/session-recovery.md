# 会话历史恢复与错误处理

本文档介绍当你因意外关闭、崩溃或网络中断丢失对话时，应用的恢复机制以及遇到问题时的处理方法。

---

## 会话是如何保存的

每次对话都会在本地留下一份完整的事件日志：你发送的消息、模型的回复、工具调用的输入和结果，都会按顺序追加写入一个文件。这份日志是对话的唯一数据来源——不是缓存，也不是摘要。

因此只要日志还在，重启后就能重新加载并继续对话。

---

## 自动恢复：大多数情况无需操作

### 正常恢复

如果在对话进行中关闭了窗口（关闭标签页、退出应用、系统重启），再次打开同一个会话时，应用会自动尝试从日志恢复。这个过程完全透明，你通常不会感知到异常。

- **已完成轮次**：如果最后一条消息已完整收到，你会看到完整的对话历史，可以无缝继续。
- **中断轮次**：如果对话在模型回复过程中被打断，界面会显示该轮次为「已中断」状态，你可以点击重试让模型从断点继续。

### 「已中断」状态的来源

当以下情况发生时，日志中会出现未闭合的轮次：

- 用户手动停止了正在运行的请求
- 进程在发送消息或接收响应途中意外终止
- 工具调用开始后但结果尚未写完时崩溃

应用会在下次打开会话时在内存中补全这些缺失的边界：

1. **未完成的工具调用**会被标记为「已中断」——每条工具调用会得到合成的错误提示，说明这次调用因中断而没有获得结果。
2. **打开的步骤**会被闭合。
3. **打开的轮次**会以 `{ reason: { kind: 'interrupted' } }` 结束。

这些合成都只发生在内存中，不会修改原始的日志文件。原始日志保持原样，以便将来需要时仍可检查。

### 关键原则

- **不截断日志**：即使在长周期任务中单个轮次可能包含大量事件，崩溃恢复也不会删除任何已提交的数据。
- **合成仅用于加载**：合成的关闭事件只在内存中使用，不会写回磁盘。
- **活跃会话不受影响**：如果某个会话仍在运行中，其打开的轮次不会被静默关闭；只有冷会话（不再活跃的会话）才会进行修复。

## 无法自动恢复的情况

如果出现以下情形，加载会失败，客户端会显示中文错误提示：

| 情形 | 原因 | 表现 |
|---|---|---|
| 日志中有序号缺口 | 某次写入中途崩溃，部分事件丢失 | 加载拒绝，提示「会话记录损坏」 |
| 日志事件乱序 | 文件系统或进程调度异常 | 同上 |
| 不支持的事件类型 | 不同版本 harness 之间的格式差异 | 提示升级或降级 harness |
| 日志文件字节损坏 | 磁盘故障、存储介质问题 | 报告具体错误信息 |

在这些情况下，不要尝试手工删除任意行、改写 `seq` 编号，也不要复制会话 id——重复的 id 会让加载直接拒绝。

## 手动恢复步骤

当自动恢复失败时，请按以下步骤操作：

### 第一步：找到会话目录

会话数据保存在以下位置之一（取决于你的平台和配置）：

```
# macOS / Linux 桌面应用
~/.coding/sessions/<项目目录>/<会话 id>/

# Linux 终端客户端（迁移前）
~/.dsh/sessions/<项目目录>/<会话 id>/
```

该目录下会有类似以下的文件：

```
session.jsonl          # 主日志（可能被压缩为 .jsonl.zst）
header.json            # 元数据头（版本、创建时间等）
attachment/            # 附件与图片
```

### 第二步：备份整个会话目录

在进行任何修改之前，把整个会话目录复制到一个安全位置：

```bash
cp -r ~/.coding/sessions/<项目目录>/<会话 id>/ \
      ~/Desktop/session-backup-$(date +%Y%m%d-%H%M%S)/
```

即使最后发现不需要恢复，备份也能让你安心操作。

### 第三步：检查日志是否完整

可以用文本编辑器打开 `session.jsonl`（如果文件被 zstd 压缩，后缀为 `.zst`，需要先解压）：

```bash
# 如果是压缩文件，先解压查看
zstd -d session.jsonl.zst -o session.jsonl

# 用 line-numbered 方式查看末尾几行
tail -20 session.jsonl
```

注意最后几条记录的 `seq` 字段是否连续。如果发现明显缺口（比如 seq 从 47 跳到 49），这就是损坏点。

### 第四步：从备份恢复或使用工具修复

如果日志结构完整但加载仍失败，可以尝试使用应用的内置修复机制（如有）。否则，从备份还原：

```bash
# 替换原文件
cp ~/Desktop/session-backup-xxx/session.jsonl \
   ~/.coding/sessions/<项目目录>/<会话 id>/
```

## 常见问题

### Q：我的会话恢复后，有些内容不见了怎么办？

如果是因为崩溃导致部分事件丢失（seq 缺口），那些丢失的内容确实无法自动恢复。但如果只是轮次被中断，内容仍在日志中——你可以在「已中断」标记处点击重试，让模型从断点继续。

### Q：我该怎么判断是「正常的中断」还是「日志损坏」？

应用会给出具体的错误提示。一般来说：
- **能自动修复**：显示为「已中断」状态，可以重试。
- **无法自动修复**：弹窗提示「会话记录损坏」或「加载失败」，此时按上述手动步骤操作。

### Q：压缩日志文件（`.zst`）损坏了怎么办？

如果压缩帧的 checksum 校验失败，说明物理层发生了损坏。这种情况下：
1. 如果有原始的未压缩副本（备份或其他同步位置），直接用原始副本。
2. 如果没有，尝试用 `zstd -d --force` 强制解压——有时尾部损坏的部分可以被跳过，前面的事件仍能恢复。
3. 如果解压也失败，只能依赖之前的备份。

### Q：跨版本升级后旧的会话还能打开吗？

每次新构建会携带一个新的 `SESSION_FORMAT_VERSION`。如果日志是用旧版本 harness 写入的，应用会尝试通过 legacy 形状归一化来兼容；如果新版格式太旧（本构建无法读取），则会提示你需要升级 harness。反之，如果日志是由更新版本的 harness 写入，则提示你升级后再打开。

目前没有自动迁移工具链——这是 deliberate 的设计，为了防止意外破坏现有数据。如需跨大版本迁移，建议先在备份上测试。

### Q：归档会话后可以找回吗？

归档只会把会话从列表中隐藏，不会删除任何数据。如果需要找回归档的会话，可以在侧边栏的「已归档」区域重新激活它。

### Q：如何彻底删除会话？

当前客户端不提供永久删除功能。如果需要彻底清理，请在关闭服务后手动删除会话目录。

## 相关概念

- **工作区（Workspace）**：会话所属的项目目录，决定了 agent 可访问的文件范围。
- **会话 ID**：每个对话的唯一标识符，由系统自动生成。
- **持久化后端**：应用支持两种存储方式——JSONL（逐文件）和 SQLite（共享数据库），两者提供相同的恢复语义。

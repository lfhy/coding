# 游戏分析

## 引擎与结构

先识别引擎（Unity、Unreal、Godot、自研），因为不同引擎的资源与脚本布局完全不同：

- Unity：IL2CPP 目标的元数据（`global-metadata.dat`）当前没有专用工具，先按容器格式读出类型、方法与字符串表；方法地址从原生二进制侧用 `open_binary` + `analyze_function` 取。Mono／托管程序集用 `inspect_managed_artifact` 与 `inspect_managed_members`。
- Flutter／Dart：`inspect_dart_aot` 读 AOT 快照。
- Godot：`.pck` 包先用 `open_binary`／`inspect_artifact` 建立清单，再按其索引格式读资源。
- Unreal：`.pak`、`.uasset`，以及蓝图与原生层的分工。
- 自研：从导入表、循环结构和资源加载路径反推。

接着找主循环：固定在某个频率上更新的函数（游戏 tick），渲染提交路径，以及输入到逻辑的入口。主循环是后面所有计时、物理、AI 结论的坐标系。

## 玩法逻辑恢复

对用户点名的机制（移动、碰撞、计分、刷怪、经济），按「状态 → 每帧更新 → 输出」拆开：

- 相关数据结构及其字段偏移，以及每个字段的读写点。
- 常量（重力、速度、冷却、概率表、阈值）在代码与数据文件里的位置。
- 更新顺序：哪些机制先算、哪些依赖上一帧结果。
- 随机源与种子（决定可复现性）。

结论要给函数与地址；从表里读出来的数值要说明表的结构与读取公式。不要只看名字猜语义——偏移、宽度与相邻访问是最可靠的路标。

## 资源与数据打包

关卡、贴图、音频与配置通常在一个容器里（`.pak`、`.assets`、`.bundle`、自定义归档）。恢复格式的方法与其它二进制格式一致：magic、版本、偏移表、压缩与加密标志、对齐、索引项。先写能列出索引的 reader，再写能取出单个资源的读取器。

## 移植到 WASM 的评估

用户想把这个游戏搬到浏览器时，评估按组件分类：

- 渲染后端（OpenGL／DirectX／Vulkan／SDL）→ WebGL/WebGPU，需要 shim 还是重写。
- 文件系统与存档路径 → IndexedDB 或 fetch 流式加载。
- 线程与同步原语 → SharedArrayBuffer／Web Worker 的能力与限制。
- 音频输出、输入处理、定时精度、平台 API、内联汇编与 64 位假设。

每一项给出「可直接移植／需要垫片／必须重写」的判断和支撑它的函数与调用点。然后给里程碑计划，终点是一个能跑的 `index.html`。若用户只要逻辑核心，优先把纯模拟逻辑（物理、AI、规则）与渲染分离，做成可在 WASM 里跑、可回放输入并比对状态哈希的模块。

## 边界

只分析用户自己拥有或获授权的游戏；离线、单机、自有测试环境。不为在线游戏制作作弊或绕过反作弊（那属于 `protection-research` 里不被允许的部分）；需要改数值时限定在用户自己的离线环境，并说明运行方式。

## 输出

引擎与版本 → 主循环与模块地图 → 目标机制的规则、常量与证据 → 资源格式细节 → （如需要）移植评估与里程碑 → 未知项。

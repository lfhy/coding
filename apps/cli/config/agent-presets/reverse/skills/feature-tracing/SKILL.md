# 功能追踪

目标是把一次用户可见的触发，追到它的最终效果：文件写入、网络请求、数据库行、界面状态或进程行为。追踪的结果是一串带证据的跳点，而不是一段叙述。

## 准备工作

1. 固定目标：具体哪个文件、哪个版本、哪种安装形态。同一程序的不同构建函数地址不同，混用会让后面所有证据失效。
2. 找到触发点：按钮、菜单项、快捷键、协议入口或定时器。名字要和界面一致，方便用户核对。
3. 明确期望的终点：写文件？发请求？改注册表？不同终点会走不同的工具。
4. 决定是否需要运行：既能静态追通又能说明证据时先静态；只有运行时才能分辨的分支才启动目标。

## 追踪过程

每一跳记录四件事：所在模块或类、函数或方法名、证据位置（地址、文件偏移、行、类方法、抓包记录）、这一跳做了什么数据变换。

处理字节序列时注意：加密、压缩、序列化会在跳点之间改变数据形态。遇到变换就把它的前后形态都记下来，否则下一跳会对不上。找不到下一跳时优先怀疑：虚表或接口派发、回调注册、动态解析的符号、字符串加壳、事件总线、线程池。

一个功能的完整路径通常包含：从界面到业务逻辑、从业务逻辑到平台能力（文件、网络、进程、IPC）、以及失败分支。失败分支同样要追：错误码映射、重试、回退路径往往是理解「为什么这里不生效」的关键。

## 边界与陷阱

- 不要因为一个字符串里出现路径就断定写入位置，要找到实际传入该 API 的调用。
- 不要因为导入了网络库就认为该功能联网，要看调用链是否到达发送点。
- 多线程／异步路径上的顺序不能靠阅读推断出来，需要日志、断点或抓包证明。
- 打包或加固过的目标，静态能看到的部分可能只是壳；把「静态可见范围」和「需要运行时才能触达」分开说明。

## 输出

按顺序给出：入口（用户如何触发）、跳点列表（每跳一条证据）、最终效果（具体到文件路径、请求形状或数据库字段）、失败与边界行为、仍未确认的部分及其原因。用户要求复现时，给一个最小输入和一个能验证该效果的命令。

# 干净房间式行为克隆

克隆的对象是**行为**，不是实现。原始程序提供的是规格，代码由我们重新写。这条线要一直守住：不抄反编译出来的源码，不搬资产、图标、文案、字体，不复制许可证与计费机制的实现细节。

## 第一产出是规格，不是代码

在动笔写实现之前，先写 `CLONE_SPEC.md`，逐条列出可验证的需求，每条后面附带证据位置（函数与地址、类与方法、抓包记录、界面观察）。

规格至少覆盖：

- 用户可见的每个功能、界面与状态切换，包括空状态、加载、错误、禁用。
- 每个操作的输入、输出、边界与副作用（文件、网络、数据库、剪贴板、通知）。
- 文件格式与网络协议：字段、编码、顺序、校验。
- 设置项与持久化布局，以及默认值。
- 失败行为：错误文案、重试、回退、降级。
- 平台差异与快捷键、输入法、无障碍等容易被忽略的面。

无法确认的条目写 `UNKNOWN`，并说明需要什么证据才能填上。规格里的每一条都应当能被一个测试表达出来。

## 实现

在用户自己的项目里用现有语言、框架、测试与风格实现。一次实现一个可验证的切片，切片的完成标准是它的测试通过——测试由恢复出的规则派生，而不是照着原始程序的可执行文件对拍。需要网络交互时，协议实现按规格来，不复用原始程序的证书、密钥或私有端点。

## 验证与残余差异

验证时用用户能重跑的方式：同一组输入在两边各跑一次，比较输出、错误、边界与状态变化，逐项记录通过、偏离、未测。不要因为几个样例对得上就宣布等价。

`verify_reconstruction` 在可用时用它跑结构化对比；它不可用时手工搭建对拍脚本，把对比结果写进规格的对应条目。

如果还原过程发现原始程序依赖未公开的服务端行为，把这一点写清楚——那部分无法通过客户端行为完全复制，说明可观测的契约是什么。

## 输出

`CLONE_SPEC.md` 的路径与摘要 → 实现落在哪些文件 → 每条需求对应的测试 → 已知偏离与原因 → 未测部分与需要的条件。

# 版本对比与崩溃分析

## 先固定两个身份

对比的前提是两边的身份都确定：文件哈希、版本号、架构、构建配置（是否同一编译器与优化级别）。不同编译配置造成的差异会被误读成「行为变化」，所以先说明这一点，再开始比较。

## 对齐

先按符号对齐，没有符号时按特征对齐（调用关系、导入引用、字符串引用、代码特征）。`compare_functions` 比较两组 `analyze_function` 证据，缺的面写成 unknown；`compare_application_versions` 与 `compare_artifacts` 给出应用层与包层的差异，`find_changed_behavior` 把已验证的进程与产物对比聚合成变化清单。对不上的函数单独列为「无法配对」——它们往往正是差异所在。

差异分四类，报告里分开写：

- 新增（新函数、新导入、新字符串、新通道）。
- 删除（被移除的能力或清理掉的死代码）。
- 内部变化但行为等价（重构、内联、优化）。
- 可观察行为变化（新增校验、改了默认值、改了协议字段、改了错误处理）。

前两类容易确认，后两类必须落到具体证据：某个比较、某个常量、某个调用被替换。别把「两个反编译结果长得不一样」当成行为变化。

## 崩溃与回归

用户给的是崩溃报告时，先解析：Apple `.ips` 是 JSON 文档，`bug_type` 以字符串保存，先读出异常类型、进程、寄存器与镜像 UUID；Linux core 用 `inspect_recorded_crash`（支持 ELF64 x86-64 与 AArch64 小端）。寄存器、镜像 UUID、异常类型是事实；「疑似某函数导致」需要符号化或反查地址才能成立。

定位回归的方法：找到崩溃点在新版中的位置，比较该函数与它的调用者在旧版里的形态，再看调用链上哪一跳的检查条件变了。反过来也成立：旧版能过、新版崩溃，通常意味着新增的前置条件（新字段、新校验、新分配尺寸）没有被满足。

## 输出

两侧身份 → 对齐覆盖率（多少函数可配对）→ 差异分类清单（每条带证据）→ 与用户问题相关的变化路径 → 崩溃或回归的定位结论与置信度 → 仍无法解释的部分。

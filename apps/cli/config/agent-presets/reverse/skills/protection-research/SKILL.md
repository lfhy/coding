# 保护措施研究

这类研究的合法目标是**评估与加固**：认清保护做了什么、覆盖到哪里、哪里薄弱。不是绕过别人的保护。

## 明确允许与不允许

允许：分析用户自己拥有或开发的软件里的保护机制；评估用户自己的反作弊／DRM／校验实现对已知攻击的抵抗能力；在用户自己的测试环境中验证结论。

不允许：为第三方软件产出绕过步骤或工具；为在线多人游戏制作作弊功能；移除第三方产品的许可证校验；协助规避计费、访问控制或内容保护。遇到这类请求，说明限制并把工作转到可做的部分——通常是识别机制、说明它对用户自有实现的启示，以及加固建议。

## 识别阶段

保护方案通常能被指纹识别：加壳段名与熵、导入表特征、反调试调用、虚拟化或控制流平坦化、完整性校验循环、TLS 回调、异常处理滥用、内核侧回调与对象回调、驱动签名与白名单、硬件侧的设备枚举与 IOMMU 状态。

对照证据描述识别结果：字符串、段、导入、调用点、注册的回调。把「像某种保护」的推断和「确认是某种保护」的事实分开写。

## 评估阶段

按攻击路径评估覆盖面，而不是笼统地说「强／弱」：

- 静态篡改：文件校验、页哈希、重定位与导入修复的检查点在哪里，是否有遗漏区段。
- 内存篡改：代码段是否只读、是否有周期性复核、校验和的输入是否可以被挑起。
- 调试与注入：检测点覆盖哪些 API 与内核对象，是否能被合法工具绕过（它们不是攻击）。
- 运行时数据：客户端信任边界在哪里，哪些判定必须由服务端复核。

对每一项给出结论、证据和残余风险。用户要在自己的产品上改进时，优先建议可验证的检测与在服务端的权威判定，而不是继续加客户端混淆。

## 边界

静态分析为默认。任何需要运行目标、附加调试器或改动系统的步骤，都要先确认目标属于用户并说明副作用。不提供可复用的绕过产物，不针对在线服务与他人设备做验证。

## 输出

识别结论（含证据）→ 覆盖面评估（按攻击路径）→ 薄弱点与残余风险 → 加固建议 → 未验证部分。

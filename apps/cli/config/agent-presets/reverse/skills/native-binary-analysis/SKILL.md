# 原生二进制分析

静态分析回答「代码里有什么」。除非另有运行时证据，不要把它写成「程序运行时会怎样」。

## 概览

先确定目标身份与前提：文件哈希、格式、架构（含位宽与字节序）、链接方式（动态／静态）、运行时（原生、.NET、Go、Rust、Electron 辅助进程等）。这些决定了后面哪些工具可用、哪些结论不可能成立。

然后给出组件地图：入口点、导出与导入、主要初始化路径、线程与消息循环、字符串与资源。用户只问「这是什么」时，停在概览并附上证据就够，不要把所有函数都反编译一遍。

## 能力分组比清单有用

把导入表按能力分组再报告，比逐个列出函数有价值得多：网络（socket、WinINet、WinHTTP、curl）、文件系统、加密（BCrypt、OpenSSL、libsodium）、进程与线程、注册表／配置、IPC（命名管道、共享内存、D-Bus）、GUI 与输入。同一组里挑出最可能属于用户问题的那些，并把其余留给后续。

字符串同样分组：路径与文件模板、URL 与域名、错误与日志文本、格式串、SQL、类名与 RTTI、版本与构建标记。命名可疑的字符串要找到引用点才算证据。

## 函数深挖

对用户关心的操作，给出：反编译伪代码（只贴相关片段）、调用者与被调用者、读写的结构体或全局、触碰的字符串与常量、地址范围。无法确定结构体布局时说明依据（访问偏移、字段宽度、编译器插入的检查），不要凭外观编字段名。

跨函数的关系优先用工具而不是阅读：调用图、交叉引用、变量值流（`trace_native_values`）比人工顺着汇编走可靠。共享代码体（尾调用、thunk、跳板）在比较两个函数时会导致误判，需要单独确认。

## 文件格式与协议

恢复格式时按字段推进：偏移、宽度、字节序、编码、约束、如何被解析、如何被写回。写成可运行的 reader 或 Python `struct` 定义，并给一个真实样本让用户自己验证。恢复网络或 IPC 协议时同样，先给出消息框架（长度前缀、magic、校验、压缩），再逐个字段；用代码里的常量构造一条样例消息，比空谈字段表有用。

## 加壳、混淆与保护迹象

高熵段、异常小的导入表、`VirtualAlloc` + `memcpy` 解壳循环、反调试导入、控制流平坦化、字符串加密都属于信号而非结论。识别到保护时要说明：静态可见范围到哪里、哪些区域只能运行时观察、分析在什么前提下可以继续。对用户自有软件做进一步解包是允许的；对第三方软件只报告识别结果。

## 工具前提

`open_binary` 需要 Hopper、Ghidra 或 IDA 之一；目标无关的 `inspect_*` 工具不需要引擎：`inspect_go_binary`、`inspect_rust_binary`、`inspect_pe_resources`、`inspect_macho`、`inspect_signature`、`inspect_binary_layout`、`inspect_wasm_artifact`、`inspect_evm_interface`、`inspect_managed_artifact`、`inspect_dart_aot`。PE 的导入表、证书表与加载配置没有独立工具：有引擎时用 `list_names`／`list_segments`／`read_bytes` 查，没有引擎时用 `readelf`／`objdump` 配合 `inspect_binary_layout` 读布局与符号。IDA 用 `provider_id: "ida"` 并传原始二进制。Ghidra 冷启动较慢（默认 330 秒），大目标先要摘要视图。

## 输出

身份与前提 → 组件地图 → 与问题相关的路径（带地址证据）→ 格式或协议细节 → 保护措施识别 → 未知项与下一步需要的证据。
